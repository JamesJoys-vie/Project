Proposed Wireframe System & Screen Flow (v2)

This document proposes an upgraded, production-grade wireframe architecture for iBanking based on the Phase 4 React/Tailwind frontend, resolving critical operational friction points identified in the original wireframes (v1). While preserving the strict low-fidelity grayscale design language, v2 elevates financial transparency, student beneficiary reusability, transaction security, and multi-step recovery states.

1. /login (Biometric/Remember) → 2. /home (Smart Overview + Quick Pay) → 3. /pay (Itemized Breakdown + Beneficiary Picker) → 4. OTP Modal (Dual Channel + Safety Recap) → 5. Official Receipt (PDF/Print + Save Student) → 6. /history (Deep Drawer + Audit Trail)
1. Beneficiary & Quick Pay Picker Replaces manual 8-digit MSSV retyping each semester with saved student profiles and recent chips.
2. Transparent Fee Breakdown Itemizes raw tuition into Base Tuition, Campus/Lab fees, and Health Insurance for complete parental clarity.
3. Slide-Over Audit Drawer Replaces dead table rows in History with an interactive slide-over showing the complete saga timeline (Reserve → OTP → Settle).
4. Banking Inactivity Session Guard Essential security compliance for financial apps: 60-second warning dialog before token expiration.

Design Innovations

  1. Fast Switch Chips for Evaluation: Eliminates repetitive password typing during testing and demonstrations without breaking actual JWT auth under the hood.
  2. Biometric / Passkey Stub: Modern FIDO2 readiness for higher education portals.
  3. Transparent Encryption & Remember Me: Adheres to banking guidelines with explicit TLS badge and device trust persistence.
Why this change? In real academic payment scenarios, parents often use mobile devices under time pressure right before registration deadlines. Streamlined authentication minimizes drop-off.

"Add Student" UI Rationale

  1. Modal Overlay: Triggered by the + Add Student ID button on Dashboard (or Checkout). The user never leaves their current context.
  2. Instant Registrar Verification: As soon as 8 digits are typed, it queries GET /tuitions/{mssv} and displays the student's legal name, faculty, and current tuition status. This guarantees the payer never saves a mistyped ID.

User Friction Prevention

  1. Gentle 404 Messaging: Avoids alarming technical database jargon; prompts user to check 8-digit format or check if term invoices are posted yet.
  2. Privacy-Preserving 409: Confirms payment date without leaking third-party reference numbers or receipts that may belong to another sponsor.
  3. Discreet Balance Alert (422): States available funds and invoice total without negative "shortfall" callouts.
  4. Concurrent Lock Awareness: Explains Redis distributed reservation holds so parents do not accidentally double-pay.
